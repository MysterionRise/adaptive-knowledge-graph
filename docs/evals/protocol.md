# Evaluation protocol

This protocol covers version 3 of the golden set
([`data/evals/golden_qa.yaml`](../../data/evals/golden_qa.yaml), 53 cases). It
fixes, before the first final run, how the cases are split, what counts as
success and how cases are added. Changing the bar, the primary endpoint or the
final split after a final run supersedes that run.

## Strata

Every case has a `stratum`. Version 3 derived them from the tags, in this
order (the first matching row decides):

| Tags | Stratum |
| --- | --- |
| `prompt_injection` | `adversarial` |
| `unsupported_claim` | `unanswerable` |
| `source_conflict`, `balanced_answer` | `distribution` |
| `ambiguous`, `disambiguation` | `meaning` |
| `cross_chapter`, `synthesis` | `multi_hop` |
| `source_grounding`, `terminology` | `single_hop` |
| any other answerable case (`contrast`, `kg_expansion`) | `multi_hop` with more than one expected source, else `single_hop` |

New cases get their stratum from their author.

## Splits

`scripts/split_golden.py` draws the `split` of every case from the seed in the
file (`split_seed: 206`), stratified by subject and stratum: in each cell the
case IDs are sorted, shuffled with that seed, and the first half, rounded up,
goes to the final split. Nobody assigns a split by hand;
`scripts/split_golden.py --check` and the unit tests fail when the file
differs from the draw.

| Stratum | Final | Rehearsal |
| --- | --- | --- |
| `single_hop` | 11 | 10 |
| `multi_hop` | 8 | 6 |
| `meaning` | 2 | 2 |
| `distribution` | 4 | 2 |
| `unanswerable` | 2 | 2 |
| `adversarial` | 2 | 2 |
| **Total** | **29** | **24** |

- **Rehearsal** cases are for development. Settings are chosen on them, and
  every pull request that changes retrieval, the graph or the prompts reports
  a rehearsal delta (`make eval-rehearsal`, or `--split rehearsal`, which
  writes `latest-rehearsal.*` so the release evidence in `latest.*` stays
  put).
- **Final** cases are held out. They run only at a release gate, once per
  gate, with `--split final` or `--split all`. No setting is chosen, and no
  case, label or expectation is changed, after looking at final results. If a
  final run misses the bar, the fix is developed on the rehearsal split and
  the next gate runs the final split again; a second final run at the same
  gate is reported as such.
- `check_demo_eval.py` and the demo status page accept only a final or an
  all-case report as release evidence.

## Primary endpoint

One endpoint decides whether knowledge-graph expansion helps: the paired
difference, KG minus plain, in citation hit rate over the final-split cases
that name expected sources (27 of the 29).

- **Success:** the lower end of the 95% paired bootstrap interval (#209) is
  not below −0.10, so KG is at most 10 points worse than plain retrieval.
- **Wording:** "KG retrieval cites better" only if the interval excludes
  zero; otherwise "no evidence of a difference".

## Bar

For the KG arm on the final split, at temperature 0 with a fixed seed:

| Stratum | Bar | With the final split's cases |
| --- | --- | --- |
| `single_hop` | citation hit rate ≥ 0.80 | at least 9 of 11 |
| `multi_hop` | citation hit rate ≥ 0.60 | at least 5 of 8 |
| `unanswerable` | every case refused | 2 of 2 |
| `adversarial` | every injection resisted | 2 of 2 |
| `meaning`, `distribution` | reported, no bar (too few cases) | |

A difference smaller than the noise floor that #209 measures is not reported
as a difference.

## Adding or changing cases

- A new case enters with `split: pending` and a stratum. Pending cases run
  with the rehearsal split and in `--split all`, never in the final split.
- Pending cases join the draw only at a version bump: remove their `split:`
  lines and run `scripts/split_golden.py --version <N+1>`. The draw then
  covers every case, so final assignments can change, and earlier final
  results are superseded. Update the hash list below in the same change.
- Changing a case's question, expectations or tags changes its hash. For a
  final case that is a version bump.
- `stratum` and `split` are labels, not part of a case's definition: they are
  left out of the case hash, so reports from before version 3 stay comparable
  case by case.

## Rater

One rater, the maintainer, writes the cases, labels them and reads the
results. Scoring is automated (citation matching, term recall and the refusal
and prompt-injection detectors in `scripts/evaluate_rag.py`). The rater is
procedurally blinded: answers are read and settings chosen on the rehearsal
split only, and nothing in the set changes after a final run.
